# Portfolio Operating Map

This file is the guardrail for long-term repository stewardship.

## Identity lanes

### MindReply Core — "the workshop floor"
Purpose: reusable business/product foundations.
Vocabulary: workshop, thread, proof, handoff, surface, release.
Do not use: generic AI dashboard language.

### A11-K — "the flight deck"
Purpose: private orchestration, owner control, and high-consequence operations.
Vocabulary: watch, command, gate, pulse, vault, dispatch.
Do not use: playful consumer language around dangerous actions.

### ReplyControl — "the reply desk"
Purpose: human communication workflows.
Vocabulary: intent, tone, queue, handoff, nudge, closure.
Do not use: robotic assistant terminology.

### Aurel — "the atelier"
Purpose: expressive, premium digital experiences.
Vocabulary: atmosphere, scene, gesture, rhythm, detail.
Do not use: operations-console language.

### MR Team — "the room"
Purpose: collaboration and shared work.
Vocabulary: room, signal, owner, rhythm, ask, done.
Do not use: enterprise-management clichés.

### Own Core — "the keyring"
Purpose: private ownership and personal control.
Vocabulary: keep, unlock, carry, boundary, archive, trust.
Do not use: surveillance language.

### Control Plane — "the watchtower"
Purpose: governance, deployment visibility, and infrastructure decisions.
Vocabulary: state, drift, checkpoint, witness, exception, rollback.
Do not use: marketing copy in operational controls.

### WhatsApp Router — "the switchboard"
Purpose: conversational routing across channels/models.
Vocabulary: route, turn, context, lane, fallback, receipt.
Do not use: model-brand-first UX.

## Automation doctrine

Every active product repository should have an hourly stewardship workflow. It may inspect, test, summarize, and open a bounded issue. It must not silently rewrite application code or deploy production.

The workflow should be offset from the top of the hour because GitHub notes that scheduled Actions can be delayed under high load around the start of each hour.

## SEO doctrine

Use a dedicated domain when a product deserves independent search identity. Avoid multiplying subdomains merely for architecture convenience. Each public site should have one clear audience, one primary intent, one canonical title system, descriptive routes, sitemap/robots coverage, and useful page copy.

## Change doctrine

Branches first. Review second. Merge last. Archived repositories are treated as historical artifacts unless explicitly revived.
